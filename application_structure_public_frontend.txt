JANNATBOOKING PUBLIC FRONTEND APPLICATION STRUCTURE
Audited: 2026-05-26

Purpose
This file documents the current public JannatBooking frontend. It is separate from the PMS/admin hotels_frontend app. It should be kept in sync with future public website, booking, SEO, chat, and SSR migration work.

Runtime
- Directory:
  - D:\JannatBooking\jannatbooking_frontend
- Framework:
  - Create React App.
  - React 18.
  - react-router-dom v5.
  - styled-components.
  - Ant Design.
  - react-helmet.
  - socket.io-client.
  - react-ga4 and react-facebook-pixel.
- Production serving:
  - server.js serves the compiled build directory with Express.
  - package.json build command: npm run build.
  - package.json start command: react-scripts start for local dev.
  - Production builds must use the production .env on the home server, where REACT_APP_API_URL is /api and REACT_APP_API_URL_MAIN is https://xhotelpro.com.
  - Do not deploy a build compiled from a local development .env with localhost API/socket values; browsers may try to contact the customer's own device, causing blank public pages and Chrome local-app/device-access prompts.
- Important limitation:
  - CRA renders metadata client-side through react-helmet.
  - Search engines and LLM crawlers that do not execute JavaScript may miss some dynamic page metadata.
  - This is the reason for the future jannatbooking_ssr sibling app.

Public Chat Widget
- Main files:
  - src/Chat/ChatIcon.js
  - src/Chat/ChatWindow.js
  - src/Chat/socket.js
- Visibility:
  - App.js hides ChatIcon when the pathname includes admin or management.
  - This keeps B2C public chat off admin/PMS screens.
- Backend endpoints now used by public chat:
  - POST /api/support-cases/new
  - GET /api/support-cases/client/:id
  - PUT /api/support-cases/client/:id
- Public chat rules:
  - Chat creates client-opened SupportCase records.
  - Public clients can append messages through the client endpoint.
  - Public clients can close/rate the case through the client endpoint.
  - Public clients cannot update support assignment, hotel assignment, AI fields, escalation fields, or admin metadata.
  - If the backend escalates a case, the public client only sees the support conversation; escalation controls/status panels remain admin-only in hotels_frontend.
  - AI messages may include conversation.quickReplies. ChatWindow renders these as compact buttons only on the latest agent message; clicking a button sends its value as a normal guest message through PUT /api/support-cases/client/:id.
  - Quick replies are used for confirmation/correction choices and optional email Skip. They must disappear after the guest sends another message so stale buttons cannot be clicked.
- Inquiry types in the public form:
  - Room pricing / availability.
  - Bed pricing / availability.
  - Payment Inquiry.
  - Update / questions about reservation.
  - Others.
- Product and AI rules:
  - This is B2C only.
  - B2B/internal chat must remain in hotels_frontend and must not use this widget.
  - Cancellation requests are human-only.
  - Reservation updates are human-reviewed.
  - Public AI assistance, when enabled backend-side, is for pricing by date range, hotels near Al Haram, payment questions, and support triage.
  - Chatbot-created reservations are shown to guests as confirmed with confirmation/details/payment links, while backend PMS/admin handling remains internally pending-confirmation.

- 2026-06-04 checkout availability rule:
  - src/apiCore.js getHotelInventoryAvailability intentionally calls GET /hotel-inventory/:hotelId/availability without a staff token from public hotel pages, cart validation, checkout, and payment flows.
  - The backend now allows this no-token request and returns only public-safe availability fields.
  - Public frontend code should rely on available plus public pricingByDay date/price/calendarBlocked data only.
  - Public frontend code must not expect rootPrice, commissionRate, agent stock fields, reserved counts, or occupied counts from this endpoint.
  - Agent-scoped availability and pending-confirmation inventory review remain PMS/admin-only and require authenticated hotels_frontend calls.
- 2026-06-04 checkout account creation and payment UX:
  - src/components/checkout/CheckoutContent.js normalizes guest details before reserve-now, pending PayPal, and final PayPal reservation calls.
  - Public checkout does not send guests to a separate signup page and must not show extra signup/account notices during checkout.
  - If the visitor is not signed in, the checkout payload includes a phone-derived temporary password so the backend can silently create a client account with the reservation.
  - PayPal pending-reservation creation validates required customer fields before opening PayPal/card payment.
  - Checkout currency conversion must only call /currencyapi-amounts with finite SAR numbers; if totals are still settling, convertedAmounts must remain null and PayPal must stay unmounted.
  - src/components/checkout/PaymentDetailsPayPal.js must not fetch the PayPal client token, mount PayPal buttons, or show generic PayPal failure toasts until the guest chose an online payment option, accepted terms, and the USD amount is positive.
  - PayPal SDK/load errors before an actual user-started payment attempt should be logged but must not show an "order failed" or generic payment-error toast to the guest.
  - If the backend returns 402 for a PayPal capture or authorization failure, the public frontend must surface that exact decline message and must not continue into success toast, redirect, or reservation-confirmed state.
  - src/pages/PaymentLink.js follows the same rule for /client-payment/:reservationId/:confirmation: validate the reservation id/confirmation/total amount first, keep PayPal unmounted until a payment option, accepted terms, positive SAR amount, and positive USD amount are all present, and suppress SDK setup errors before a real payment attempt.
  - src/pages/PaymentLink.js reserves mobile top spacing for the fixed navbar so the public payment card never starts underneath the logo/header.
  - src/components/Navbar/Navbar.js initializes the transparent top-of-home state only on /; public checkout/payment routes must render the solid navbar immediately without waiting for a scroll event.
  - Generated payment links must never render PayPal/card controls beside blank reservation fields, missing dates, or 0 SAR/0 USD amounts.
  - After successful paid reservation creation, the user always redirects to /reservation-confirmed even if automatic sign-in fails because the email already belongs to an older account with another password.
  - src/pages/ConfirmationPage.js must show the normal reservation confirmation only; account/password management can happen later from the user account area.
  - Error messages should stay descriptive for missing guest details, unavailable rooms, declined payments, and backend reservation failures.

2026-06-08 Jannat Concierge Transfer UX Contract

  - The hotel assistant reply is intentionally delayed by roughly 5-8 seconds by default so the transfer feels like a real handoff instead of an instant persona swap.
  - If a guest sends a message during the transfer pause, the backend handles it in the hotel scope and may cancel the pending intro.
- Public widget expectations:
  - Render system transfer messages as normal conversation messages.
  - Keep showing quickReplies only on the latest agent/system-supported message, as the current component does.
  - Hotel option, Confirm / Something is wrong, and Skip email quickReplies are backend-provided; the widget should only send the clicked value back as a normal guest message.
- Date/language expectations:
  - If the guest writes a Ramadan/Hijri date range, backend replies may include both Hijri and Gregorian/Miladi dates in the same message.
  - No-year Ramadan wording is interpreted by the backend as the upcoming Ramadan; frontend should not add its own date assumptions.
